# نشر النظام على خادم إنتاج

هذا الدليل للمسؤول التقني الذي سيُشغّل النظام لأول مرة على خادم حقيقي. الترتيب مقصود: كل خطوة تعتمد على ما قبلها.

> **قبل كل شيء:** النظام يرفض الإقلاع إذا بقيت إعدادات التطوير مع `DEBUG=false`. هذا متعمَّد — الفشل الصريح عند الإقلاع أرحم بكثير من نظام يعمل بمفتاح توقيع معروف وكلمة مرور منشورة.

---

## 1. متغيّرات البيئة

انسخ `backend/.env.example` إلى `backend/.env` وغيّر التالي **كلّه**:

| المتغيّر | القيمة | لماذا؟ |
|---------|--------|--------|
| `DEBUG` | `false` | يُخفي صفحات التوثيق التفاعلية `/docs` و`/redoc`، ويُفعّل كل الفحوصات أدناه |
| `SECRET_KEY` | مفتاح عشوائي جديد | به تُوقَّع جلسات الدخول؛ من يعرفه يستطيع انتحال أي مستخدم |
| `FIRST_ADMIN_PASSWORD` | كلمة مرور تختارها | القيمة الافتراضية منشورة في هذا المستودع، أي أنها معروفة للجميع |
| `AUTO_CREATE_TABLES` | `false` | يُنشئ الجداول الناقصة ولا يُعدّل الموجود، فيُخفي انحراف المخطط بدل إصلاحه |
| `DATABASE_URL` | رابط قاعدة الإنتاج | — |
| `CORS_ORIGINS` | نطاق الواجهة فقط | لا تترك `localhost` |

لتوليد مفتاح جيد:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

**لا تضع `.env` في Git.** تحقّق أنه مذكور في `.gitignore`.

---

## 2. قاعدة البيانات

المخطط يُبنى بالترحيلات (Alembic) **حصراً**:

```bash
cd backend && alembic upgrade head
```

شغّل هذا الأمر عند كل إصدار جديد، **قبل** تشغيل التطبيق. لا تستخدم `AUTO_CREATE_TABLES` بديلاً عنه أبداً: هو يُنشئ الجداول الناقصة ولا يُعدّل عموداً واحداً في جدول موجود، فيُقلع التطبيق بنجاح على قاعدة لم يُنتجها أي ترحيل — ثم يظهر الخلل لاحقاً كإدخال فاشل. هذا ليس افتراضاً؛ حدث فعلاً أثناء التطوير.

---

## 3. النسخ الاحتياطي — قبل أول فاتورة

**لا تُدخِل بيانات حقيقية قبل أن تعمل نسخة احتياطية وتُختبر استعادتها.** نسخة لم تُجرَّب استعادتها ليست نسخة احتياطية، بل أمنية.

نسخة يومية:

```bash
pg_dump -Fc -h HOST -U USER -d erp -f "erp-$(date +%F).dump"
```

الاستعادة (على قاعدة اختبار أولاً):

```bash
pg_restore -h HOST -U USER -d erp_restore_test --clean --if-exists "erp-2026-08-05.dump"
```

القواعد الثلاث:

- **احتفظ بعدة أجيال** (يومية لأسبوع، أسبوعية لشهر) — لأن أسوأ الأعطال هو تلف بيانات لا يُلاحَظ فوراً، فتُصبح آخر نسخة تالفة أيضاً.
- **احفظ نسخة خارج الخادم.** نسخة على نفس القرص تحمي من خطأ بشري لا من عطل قرص.
- **جرّب الاستعادة شهرياً** على قاعدة منفصلة، وتحقّق أن ميزان المراجعة متوازن بعدها.

---

## 4. أول تشغيل

1. شغّل الترحيلات (خطوة 2).
2. شغّل التطبيق مرة واحدة — يُنشأ حساب المدير الأول بالقيم التي ضبطتها.
3. **سجّل الدخول فوراً وغيّر كلمة المرور** من شاشة المستخدمين.
4. أنشئ حساباً منفصلاً لكل موظف. **لا تُشارك حساب المدير**، فسجلّ التتبّع يوثّق باسم الحساب لا باسم الشخص الجالس أمام الشاشة.
5. اضبط بيانات الشركة والضريبة من **الإعدادات** (الفصل 2 من دليل المستخدم).

---

## 5. الشبكة

- **HTTPS إلزامي.** التطبيق يُرسل رموز الدخول في ترويسة `Authorization`؛ بدون تشفير النقل تُقرأ على الشبكة نصاً صريحاً. ضع الخادم خلف وسيط عكسي (Nginx/Caddy) بشهادة صالحة.
- **لا تفتح منفذ قاعدة البيانات على الإنترنت.** الخادم وحده يصل إليها.
- `CORS_ORIGINS` نطاق الواجهة فقط، لا `*`.

---

## 6. تحقّق قبل التسليم

| الفحص | الطريقة | المتوقّع |
|-------|---------|----------|
| الإعدادات آمنة | شغّل التطبيق بـ `DEBUG=false` | يُقلع دون شكوى؛ وإن اشتكى فالرسالة تُسمّي ما ينقص |
| التوثيق مخفي | افتح `/docs` | 404 |
| المخطط محدَّث | `alembic current` | يطابق آخر ترحيل |
| كلمة المرور غُيّرت | ادخل بالافتراضية | يُرفض الدخول |
| النسخة الاحتياطية تعمل | استعِد على قاعدة اختبار | ميزان المراجعة متوازن |
| النسخة الاحتياطية آلية | راجع جدولة المهام | تعمل يومياً بلا تدخّل |

> **الصف الأخير هو الذي يُنسى غالباً.** نسخة احتياطية تحتاج من يتذكّرها كل يوم ستتوقف في أول أسبوع مزدحم — وهو بالضبط الأسبوع الذي ستحتاجها فيه.
